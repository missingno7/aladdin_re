# The Z80 bank guard of `al_atomic`: is it too conservative during the driver's bit-serial bank write? (16 September 2026)

A read-only study.  Nothing under `src/`, `native/`, `tests/`, the histories, the fixtures or the
product artifacts was changed; nothing was rebuilt; nothing is committed.  Everything below ran
against HEAD `bdb2153` with the working tree's uncommitted adapter (`al_abi() == 3`, `Machine.refusal`)
and the production binary `build/libgenesis_native.dll` (SHA-256 `bb3479af…`); the working-tree diff
of `src`/`native`/`scripts` at the time had digest `47497507…` (each artifact of this study records
this provenance under `provenance`).  Scripts are `scripts/research/zb_*.py`; artifacts are under
`artifacts/gods/research/z80-bank-guard/`.  "Measured" means a number produced here with the named
script; "static" means read from a disassembly; "inferred" is marked as such.

The question is only this: is the pre-check
`if (m.z80.running() && (uint32_t(m.z80.bank) << 15) >= 0xe00000u) return;` (`native/machine.cpp`,
`al_atomic`) unnecessarily conservative during the sound driver's nine-write bank-register
transition, and if so what narrower guard would be provably safe?

---

## 1. The invariant the guard protects, and why there are two guards

### 1.1 What an atomic span does to the Z80's view of time

`al_atomic` stages a `GenesisNativeOperation` whose `execute` closure applies every plan write and
register field at once; the engine (`port_forge/src/host/genesis_engine.hpp`, the boundary lambda)
runs it as one region:

    machine_.run_sound_processor();     // the Z80 caught up to the gate instant (a no-op at a parked gate)
    operation();                        // ALL plan writes land now, then cpu_cycles += cycles
    machine_.sync();                    // master time advances by the whole span
    machine_.run_sound_processor();     // the Z80 now executes the WHOLE span, after every write

In the original execution the same span is N instructions with the Z80 caught up at every boundary,
so a Z80 window access at instant t inside the span sees the work RAM as the instructions completed
before t left it — possibly an intermediate value the plan does not even contain (a plan is a final
effect; intermediate stores are elided).  Under the atomic operation the same access sees the
end-of-span RAM.  Symmetrically a Z80 *write* into work RAM at t is, in the original, visible to the
68000's later reads in the span and may be overwritten by its later stores; under the atomic
operation it lands after every plan write and is missed by the plan's reads.  Either way the machine
after the span differs from the original's, and the difference is invisible to every 68000-side fact
the qualification compares (the plan's own reads and writes are exact); it surfaces only as a
desynchronised sound co-processor (the ledger's 00BA8E entry records precisely such a defect being
caught by the eight-recording tree and by nothing smaller).

So the invariant is: **an atomic span is admitted only if no Z80 window access to work RAM occurs
inside it; if one does occur the machine is invalidated rather than continued.**  (Reads and writes
alike: the adapter's hook ignores the write flag.)

### 1.2 Where the window goes: `at >= 0xE00000`

The Z80's 8000–FFFF window is decoded by the box (`port_forge/src/platform/genesis/z80_box.hpp`,
`own_read`/`own_write`) as `(bank << 15) | (at & 0x7FFF)` and handed to the machine's
`window_read`/`window_write` (`machine.hpp`): an address below the ROM size is the cartridge (writes
into it are discarded — the mask-ROM rule the file documents with Gods' own channel claim), an
address `>= 0xE00000` is the 68000's 64 KB work RAM mirrored through E00000–FFFFFF
(`mem.memory[kWorkRamBase | (at & 0xFFFF)]`, the same bytes `al_ram` exposes), anything else refuses
by name (`genesis.z80.bank_window`).  Hence `at >= 0xE00000` in the observer means exactly "this
access is served from the work RAM the plan writes", and `(bank << 15) >= 0xE00000` means
`bank >= 0x1C0`: the three most recently shifted-in bits are all ones.

The register itself is a shift chain, not a byte (`own_write`, 6000–60FF): each write shifts the
value right by one and inserts bit 0 of the written byte at the top,
`bank = (bank >> 1) | ((value & 1) << 8)`, `++bank_bits`.  Nine writes, least significant address bit
(A15) first, select a bank; the value between writes is a mixture of the old bank's high bits and
the new bank's low bits.  The 68000 never touches the register in either game (the box refuses
`genesis.z80.bank` on a 68000 access; the Gods sweep disassembly's only Z80-space accesses are the
driver upload and the mailbox transfer at `0F4478`–`0F4538`).

### 1.3 The two guards and their failure modes

`al_atomic` has both a **pre-check** (before any effect: refuse with `*accepted = 3` while the Z80 is
running and its register points at work RAM) and an **observer**
(`host.observe_window`, installed for the duration of the engine call and cleared by the `Clear`
scope; throws `std::runtime_error("Atomic shared-RAM guard: Z80 window observed work RAM")` on any
window access with `at >= 0xE00000`).

They are not redundant, because their consequences differ:

* the pre-check is a *graceful* refusal: nothing is applied, the executor stays parked at the gate,
  the dispatcher falls back to the original for one instruction (`Candidate._fallback`);
* the observer fires only *after* `operation()` has applied the writes and the Z80 has been run part
  of the way through the span.  The throw leaves the engine's boundary lambda, the run ends
  `FrameworkException`, and `al_atomic` sees `e.completed && classification != ExecutionSuspension`,
  sets `h.failed = true` and raises "Atomic execution failed; machine invalidated".  There is no
  rollback: `docs/common/machine-ownership.md` — "A failure after effects invalidates execution;
  never rerun the original over a partially applied replacement."  A verification run dies there.

The pre-check therefore exists to keep the *likely* shared-RAM case out of the fatal path: a driver
that has banked work RAM has banked it in order to read it, so a span would very probably trip the
observer.  The comment in `al_atomic` says as much: "A currently shared bank is outside this atomic
domain.  A bank change during the span is also watched before its first RAM access below."  The
existing test `tests/common/test_atomic_sound_guard.py` exercises exactly this split with a
synthetic cartridge whose Z80 writes nine one bits (bank `1FF`, window `FF8000`): test 1 parks the
gate after the writes and expects a refusal with the snapshot unchanged; test 2 parks the gate
before the writes with a Z80 that then reads `8000` and expects the invalidation.

A third fact keeps the pre-check sound for the whole span: `running()` at the gate holds until the
span ends, because a plan may only write work RAM (`Atomic writes require work RAM`), so it cannot
release or take the Z80's bus or reset line.

## 2. The Gods driver's transition, measured

### 2.1 The code (static)

The 68000 copies ROM `0F4570`–`0F55E3` (0x1074 bytes) to Z80 RAM 0000 once, from the boot path
(`0003AA jsr $f44ce`; `0F44CE` is called from nowhere else), after storing the two bank cells: `0F454C`
writes the bytes of `$000F0000` to `FFDC14`–`FFDC17` and of `$000F8000` to `FFDC18`–`FFDC1B`, which
`0F4516`–`0F4524` copies to Z80 RAM `1FA6`–`1FAD`.  The disassembly
(`scripts/research/zb_z80dis.py`, output `artifacts/gods/research/z80-bank-guard/gods-z80-driver.asm`)
has exactly four writes to `6000`, in two routines:

    013C  ld hl,($1FA8)      ; routine A: cells 1FA6/1FA8 = 000F0000 -> bank 01E, window 0F0000
    013F  xor a
    0140  sla h              ; carry = A15
    0142  adc a,$00
    0144  ld ($6000),a       ; write 1
    0147  ld hl,($1FA6)
    014A  ld b,$08
    014C  xor a
    014D  sra l              ; carry = A16 .. A23, one per iteration
    014F  adc a,$00
    0151  ld ($6000),a       ; writes 2..9
    0154  djnz $014C
    0156  ld de,($1FA8)      ; then: window pointer ix = 8000 + (offset & 7FFF) -> (0D0F)
    ...
    0168  ret
    0169  ...                ; routine B: the same shape over cells 1FAA/1FAC = 000F8000 -> bank 01F, window 0F8000
    0171  ld ($6000),a       ; write 1
    017E  ld ($6000),a       ; writes 2..9
    0195  ret

Between the first and the ninth write both routines execute only register operations and reads of
their own RAM (`1FA6`–`1FAD`); the first window access is after the `ret` (the handler's
`(ix+n)` reads at `0196`–`0254` for A; the main loop's DAC sample read `012F ld a,(hl)` for B).  The
bank cells are read-only to the Z80 (every reference is `ld hl,(nn)`/`ld de,(nn)`) and are written
by the 68000 only in the one-time upload.  So the driver has exactly two completed bank values, `01E`
(ROM `0F0000`) and `01F` (ROM `0F8000`), and can never bank work RAM.

Routine A is called at IRQ entry (`004F`) and once at init (`0004`); routine B at IRQ exit (`00F5`).
Interrupts are disabled throughout the handler (IM 1 entry; `ei` only at `010F` before `reti`) and
during init (`di` at `0000`, `ei` at `000C`), so no Z80 interrupt can interleave a window access into
a sequence; the Mega Drive wires no NMI.  The DAC playback (`0112`–`013A`) reads sample bytes
through the window at bank `01F` between interrupts.

### 2.2 The register's values during the transition (static, confirmed by measurement)

From `01E` to `01F` (routine B writes 1,1,1,1,1,0,0,0,0): `10F`→`187`→**`1C3`**→**`1E1`**→**`1F0`**→
`0F8`→`07C`→`03E`→`01F`, i.e. windows `878000`, `C38000`, **`E18000`, `F08000`, `F80000`**, `7C0000`,
`3E0000`, `1F0000`, `0F8000`.  From `01F` to `01E` (routine A writes 0,1,1,1,1,0,0,0,0):
`00F`→`107`→`183`→**`1C1`**→**`1E0`**→`0F0`→`078`→`03C`→`01E`, windows `078000`, `838000`, `C18000`,
**`E08000`, `F00000`**, `780000`, `3C0000`, `1E0000`, `0F0000`.  Three consecutive one bits are what
puts the register at or above `1C0`; both sequences pass through that state and leave it at the
sixth write.

### 2.3 Measured on the machine

`scripts/research/zb_bank_trace.py` runs the original from `boundary-6000` and samples the Z80 box
out of a snapshot at every 68000 instruction boundary from raster line 220 to line 60 of the next
frame (a 68000 instruction is at least 28 master ticks = 1.87 Z80 T-states, so every Z80
instruction boundary is sampled).  Twelve frames, 41,038 samples
(`artifacts/gods/research/z80-bank-guard/bank-trace-6000-12.json`):

| sequence | when | writes | duration | windows `>= E00000` | interval in that state |
|---|---|---|---|---|---|
| A (`01F`→`01E`) | raster line 224.94–228.07, every frame | 9 | 10,346–10,626 master ticks | `E08000` (write 4), `F00000` (write 5) | 1,316–1,372 ticks = 188–196 68k cycles = 0.4 lines |
| B (`01E`→`01F`) | raster line 16.8–56.6, varying per frame | 9 | 5,320–5,762 master ticks | `E18000` (3), `F08000` (4), `F80000` (5) | 2,086–2,602 ticks = 298–371 68k cycles = 0.6–0.8 lines |

Sequence A takes twice as long as B because the 68000's VBlank sound transfer (`0F4478`–`0F449E`)
takes the Z80's bus while A is at its first write (63 samples with the bus taken at phase 1, 68000
PCs `0F4480`–`0F449E`); the parked Z80 resumes the sequence when the bus is released — its
instruction order is unaffected.  In every sample whose window was at or above `E00000` the Z80's PC
lay inside the executing routine and IFF1 was clear: **0 violations in 41,038 samples**.

The census over 3,000 frames from power-on (`zb_bank_census.py --game gods`, 8 samples per frame,
`bank-census-gods-3000.json`) sees completed values `01F` (19,729 samples), `01E` (4,108) and `000`
(6, before the driver starts) and nothing else; 18 writes per frame in 2,990 frames, 9 in 3 (the
boot frames); **no completed value ever points at work RAM**.

| window | frames | admitted | `z80_bank` refusals | windows at the refused gates | phase (`bank_bits mod 9`) | Z80 PC at the gate | raster lines |
|---|---|---|---|---|---|---|---|
| `boundary-6000` | 600 | 7,486 | 47 | `E18000` 17, `F08000` 18, `F80000` 12 | 3: 17, 4: 18, 5: 12 | `0179`–`0181` (routine B, writes 3–5) | 10–49 |

deadline and 2 engine refusals: the bank guard is essentially the whole remaining adapter residue.

## 4. Does the observer cover what the pre-check would stop covering?

### 4.1 Coverage inside admitted spans (measured)

An admitted span's Z80 catch-up runs with the observer armed.  The probe counts, for every admitted
span, the bank writes that fell inside it (bit count after minus before) and replays the shift
register over those bits to know which windows it passed through:

| window | admitted spans | containing bank writes | whose register passed through a work-RAM window inside the span |
|---|---|---|---|
| `boundary-6000`, 600 frames | 7,486 | 178 | **105** (`E18000` 105, `F08000` 87, `F80000` 78) |
| `boundary-12000`, 600 frames | 7,509 | 172 | **82** |
| `boundary-6000`, 6,000 frames | 70,879 | 1,136 | **522** (`E18000` 522, `F08000` 410, `F80000` 315) |

In all 604 distinct spans (the 6,000-frame window contains the 600-frame one) the observer was armed while the register transiently pointed at work
RAM, the driver went on to read the window after its ninth write (at bank `01F`, ROM), and the
observer did not fire — the runs continued and the candidate's trajectory is the one the tree
verified bit-exact.  That is the direct measurement that the transition, as the driver performs it,
contains no window access at a RAM value; the only thing the pre-check adds on Gods is refusing the
spans whose gate happens to be parked *during* the three-to-five-write window.

### 4.2 The positive cases on the machine (`scripts/research/zb_adversarial.py`, `adversarial.json`)

Synthetic cartridges in the shape of the existing test, each in its own process; the span asks for a
2,000-cycle operation writing `FF8000`:

| case | Z80 program | state at the gate | `Machine.atomic` | machine |
|---|---|---|---|---|
| P1 | nine one bits, then `jr *` | bank `1FF`/`FF8000`, phase 0 | **refused: `z80_bank`** | valid |
| P2 | nine one bits, then `ld a,(8000)` loop; gate before the writes | bank `100`, phase 1 | **error: "Atomic execution failed; machine invalidated: Atomic shared-RAM guard: Z80 window observed work RAM"** | invalidated |
| P3 | three one bits, then `ld a,(8000)` loop; gate after the writes | bank `1C0`/`E00000`, phase 3 | **refused: `z80_bank`** | valid |
| P3b | the same program, gate before the writes | bank `100`, phase 1 | **invalidated** by the observer (the read through the transient window) | invalidated |
| P4 | nine zero bits, then `ld a,(8000)` loop | bank `000`, phase 0 | admitted | valid |
| P5 | three one bits, then `jr *` | bank `1C0`/`E00000`, phase 3 | **refused: `z80_bank`** although the span would be exact | valid |

P3b is the adversarial positive case for any narrowed rule: a Z80 that accesses the window while its
sequence is incomplete and the register transiently reads as work RAM.  The observer catches it
(fatally); the pre-check catches it gracefully only when the gate is parked after the writes (P3).
**No such program exists in either game's driver** (§2.1 for Gods; §4.3 for Aladdin) — the transient
values are an artifact of the shift chain that a driver would only observe by accident.  P5 is the
Gods case: a transient with no access, refused today.

### 4.3 Aladdin's driver (static, plus a census)

Aladdin's driver (ROM `1B8480`–`1B9D05`, uploaded by `1E573A`; disassembly
`aladdin-z80-driver.asm`) writes `6000` in one routine only, `023D`: `ld de,$6000` then nine
`ld (de),a` in a straight line (A15 from `rlc` of h, A16–A23 from `rra` of b), followed by
`set 7,h` and an `ldir` that copies sample data from the window into Z80 RAM.  The routine calls
`02B7` before the first write and after the ninth, never between; `02B7` is self-modified into
`exx; ex af,af'` and serves the DAC from the shadow-register pointer in Z80 RAM (`de'` = `1Fxx`),
not from the window.  Interrupts are enabled in the main loop but the IRQ handler `0038` is
`ld ($003E),sp; reti`.  The banks come from the four ROM tables the game passes at init
(`1AA344`: `1B9D06`, `1BAF46`, `1BAF6F`, `1C73CB`).  The census over 3,000 frames from power-on
(`zb_bank_census.py --game aladdin`, `bank-census-aladdin-3000.json`) sees completed values
`037`–`03C` only (ROM `1B8000`–`1E7FFF`), up to 20 sequences per frame while samples stream, and
transient values with work-RAM windows at phases 3–8 (`1C6`, `1C0`, `171`, `181`, `1B1`); **no
completed value points at work RAM.**  Aladdin's driver transitions therefore also refuse today's
pre-check by chance, at more phases than Gods', and are equally free of window accesses inside a
sequence.  How often Aladdin's history verification hits the refusal was not measured here.

## 5. Candidate narrower rules

Every rule below keeps the observer unchanged, so the invariant of §1.1 holds for every rule; what
differs is which spans are refused gracefully and which are left to the observer's fatal path.

**R0 — current.**  Refuse while `running() && (bank << 15) >= E00000`.  Graceful for P1, P3, P5;
fatal for P2, P3b.  Refuses every transient-window gate: 4,223 spans on the Gods tree.

**R1 — completed sequences only.**  Refuse while `running() && (bank << 15) >= E00000 &&
bank_bits % 9 == 0`.
*Invariant preserved:* the same as R0 (the observer is untouched); additionally, every value the
pre-check refuses is a bank a driver actually selected, not a shift-chain intermediate.
*Positive case it must still refuse:* P1 (test 1 of `test_atomic_sound_guard.py`) — phase 0, bank
`1FF`.  *What it hands to the observer:* P3/P5-shaped programs; on both real drivers that set is
empty (§2.1, §4.3), and P3b already shows the observer's verdict for the one that is not.
*Measured effect:* admits 47/47, 58/58 and 379/379 of the probed refusals (§3); on none of them
would the observer have fired, by the argument of §2.1 and the 604 admitted spans of §4.1 that
covered the same transients with the observer armed.
*Caveat — the phase:* `bank_bits` counts from the machine's construction (`Z80Box::reset()` is
called only from the constructor; a Z80 reset from `A11200` does not clear it; snapshots carry it).
The count stays aligned as long as every sequence is nine writes and no upload interrupts one; Gods
uploads once at boot (`0003AA`) before the Z80 has ever run, and every value measured over 3,000
frames and every refusal over 6,600 frames was in phase.  If the phase ever drifted, R1 errs only
towards R0 (refusing a transient as if complete) or towards the observer (admitting a completed RAM
bank that a non-accessing driver would make exact and an accessing one would turn into an
invalidation) — never towards a silent divergence.
*Validation plan:* (i) `tests/common/test_atomic_sound_guard.py` unchanged and green (P1 refused
before effects, P2 invalidated); (ii) two new tests in the same shape: P5 admitted and bit-exact
against the interpreted span (the positive control for the relaxation), P3 parked after three writes
now invalidated (documenting the new fatal case by name); (iii) the negative control: the Gods
eight-recording tree at the product instant (`verify_status`/`execute_history(tree=True)`) equal to
the current reference on every field of every frame, with the `z80 bank guard` fallback class at 0
and no invalidation, and the Aladdin verification set unchanged; (iv) the refusal probe re-run to
show the class gone rather than re-labelled.

**R2 — observer only.**  Drop the pre-check.  Same invariant; loses the graceful refusal of a
*completed* RAM bank (P1 becomes an invalidation the moment such a driver reads the window).  On
both games it admits exactly what R1 admits, because neither ever completes a RAM bank, so it buys
nothing over R1 and gives up the one graceful case a future game might need.  Not recommended.

**R3 — snapshot-protected admission.**  Keep R0's condition but, when it trips, take a native
snapshot, admit with the observer armed, and on an observer throw restore the snapshot, truncate the
PCM the partial span produced and report `*accepted = 3`.  Exact and graceful in every case,
including P3; costs an adapter change with a restore path inside `al_atomic` (executor flags
`yielded`/`staged`, scheduler latches, `h.pcm`), and a snapshot per tripped gate (~0.4 % of calls).
Needs a prototype and a cost measurement; it is the only rule that would also cover a driver that
does bank work RAM without ever invalidating a run.

**R4 — a declared safe PC range.**  Admit a transient only while the Z80's PC is inside the
driver's bank routine.  Game facts in the adapter, which `machine.cpp` deliberately holds none of; a
profile-declared range through the ABI would be the honest form.  R1 achieves the same admission set
on both games without the fact, so R4 is not worth its plumbing unless a driver appears that
accesses the window mid-sequence *and* must be supported — then R3 is the better answer anyway.

## 6. Recommendation

**Safe to adopt, with the named proof and negative control: R1** — refuse only a *completed*
nine-bit bank that points at work RAM (`bank_bits % 9 == 0`), leaving transients to the unchanged
observer.  Proof: §1 (the observer alone carries the invariant; the pre-check only selects the
graceful path), §2.1 and §4.3 (neither driver accesses the window between the first and ninth write
— four write sites in Gods, one in Aladdin, all straight-line, no interrupt can interleave), §2.3
and §4.1 (0 violations in 41,038 instruction-granular samples; 604 admitted spans covered the
transients with the observer armed and it never fired).  Negative control: the tree and the Aladdin
verification unchanged, the fallback class at zero, the existing guard tests green plus the two new
ones in §5.  Expected gain on Gods: 4,223 fewer fallbacks on the tree (≈0.4 % more admitted spans);
the residue that remains is the deadline/VBlank classes and the declined arms.

**Needs more evidence: R3** (a prototype of the restore path and its cost, and a decision on
whether a run should ever be allowed to continue past a shared-RAM access at all — today the
ownership doc says it should not, and R3 would honour that by restoring, not by continuing).  Also
the frequency of the refusal on Aladdin's history verification, if R1 is meant to help there.

**Do not change:** the observer, its `at >= 0xE00000` threshold (it is exactly the machine's own
work-RAM decode), the `running()` condition, or the fatal consequence of an observer hit (no rerun
over partial effects).  R2 and R4 are not recommended for the reasons in §5.
