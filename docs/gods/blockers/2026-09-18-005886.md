## Observed

A full census (`census_all.py --entry 0x005886`, five recordings, 190
retained fixtures) buckets by `last_pc` into **ten** distinct terminal
addresses -- not the "one or two arms" shape every leaf recovered this
session (8, 13, 12, 16, 11) has had -- and tracing several of them by hand
(`pathfacts.trace`/`pathfacts.report`, since linear disassembly across
this range earlier this session produced garbled instructions from data
embedded in code) shows the state is at least three separable pieces, none
of them a small leaf:

- **The head gate** (`005886`-`005D30`ish) splits on `FFFFEA1E == 1`.
  The `!= 1` arm (`0058D2` onward, the majority: 19+11+20+20+20+21+22 =
  133 of 190 fixtures land past it) runs an UNCONDITIONAL 200-entry
  inline scan at `0058D8`-`005924` that is the SAME algorithm as the
  already-recovered `game.movement.box_overlap_scan` (`00722C`, shared by
  states 0/1): the same table (`FFFF4342`), the same 8-byte stride, the
  same per-entry skip tests (`+4` negative, `+6` zero) and the same box
  margins against the tracked position (`FFFFF18C`/`F18E` offset by
  `0x10`/`0x28`, entry box `-4`/`+0x14` x, `-0xC`/`+0x10` y) -- confirmed
  instruction-by-instruction against a real trace, though the two copies
  are NOT byte-identical (the state 19 copy computes the margin sum with
  `moveq`+`add.w` inline rather than `00722C`'s own opening sequence, so a
  raw ROM diff at the expected offset does not line up; a `bsr` into
  `00722C` itself is not the shape here -- this is a second, separately
  compiled copy of the same source algorithm, not a call).  Unlike
  `00722C`'s own two witnessed call sites (states 0/1, where the scan's
  result is discarded), state 19's OWN copy is used: the found entry's
  `+4` field is read as an object-kind index into a 192-entry ROM table
  at `0x14B42` (`cmpi.b #2,(a2,d2.w)`), and a kind of exactly 2 disables
  the table slot (`+4` set to `-1`, matching the scan's own "skip
  negative" test) unless a further `FFFFEA23` bit-1/bit-2 gate is clear,
  in which case the slot is instead re-armed (`+4` restored to the kind
  value, `+6` set to 1) and a "scan already ran this tick" latch
  (`FFFFF238`) is cleared again.  This reads as a "one nearby interactive
  object, once per activation, arms or permanently disables itself"
  scan -- structurally close to the already-recovered
  `hazard.proximity_search`/`pickups.contact_search` shape, but over yet
  another table with its own record layout and its own 192-entry ROM
  type table, neither read by anything already recovered.
- **`FFFFEA1E == 1`** (the other head arm, `0058A2`) is a small dispatch
  over TWO flag words, `FFFFF238` (a "scan in progress" latch the OTHER
  arm's own scan sets) and `FFFFF23A` (a "scan found nothing" latch that
  same scan's own exhausted-`dbra` tail sets): zero/zero calls the shared
  leaf below directly; the "already ran, found nothing" combination
  additionally gates on `FFFFEA23` bits 1/2 before calling it; the
  "already ran, still searching" combination exits unchanged
  (`0058AE beq.w $5c5e`, `0058B8`/`0058C2`'s own `bne.w $5c58`) without
  the call at all.  This means the SAME 200-entry scan above and this
  small dispatch are two ends of one state machine spread across BOTH
  head arms, not two independent gates.
- **`005CEE`** (called from three different points across both head arms)
  is a NEW leaf that reuses fields this session already believed
  understood, incorrectly: `game.achievements.ACHIEVEMENT_SLOTS`
  (`FFFFF22E`) and `HIGHLIGHT_ID` (`FFFFF236`) are NOT specific to the
  achievement/collectible-slot tracker as `achievements.py`'s own module
  docstring claims -- `005CEE` indexes `ACHIEVEMENT_SLOTS` directly by
  `FFFFF236` (`lea f22e.w,a3; move.w f236.w,d4; add.w d4,d4; move.w
  (a3,d4.w),d2`), a different addressing convention than
  `achievement_slot_reset`'s own four fixed offsets, and calls into the
  SAME already-recovered icon-upload seam (`001648`) with `d1` FORCED to
  1 (`achievement_slot_reset`'s own "highlighted" case, never computed
  here) on the common arm, but on the other real arm (`005CFE`'s own
  `bmi` NOT taken, i.e. the slot is NOT empty) instead calls a THIRD,
  completely unrecovered leaf, **`010D7C`**, with the tracked position
  (`FFFFF18C`+8, `FFFFF18E`+0x20) and a kind word, storing them into FOUR
  fields no already-recovered code touches (`FFFFF1F0`/`F1F2`/`F1F4`/
  `F1F6`) gated by a busy test on `F1F6` itself and a special-cased kind
  (`cmpi.w #$3d,d2`) that branches elsewhere inside `010D7C` before the
  stores. This is a fourth subsystem (a floating icon/message SPAWN record,
  distinct from `game.messages`'s own `MESSAGE_BOUND`/`MESSAGE_BUFFER`
  fields, `FFFFF164`/`F166`/`F16A`/`F16E`) with its own busy/kind gating
  this session has not traced past its first branch.
- **At least five more terminal shapes** (`5C54` 22, `5C78` 21, `5C80`
  20, `5C94` 20, `5CEA` 20 of the 190 retained fixtures -- more than half
  the census) reached through `FFFFEA23` bit tests around `005C14`-
  `005C4A` this session has not traced at all: their own targets are
  past the point this investigation reached.

## Why the current mechanism does not fit

Every state this session recovered (8, 13, 12, 16, 11) is a single
gate-then-tail shape, or (13/12) a small number of sub-arms sharing one
tail, costed and boundary-planned in one sitting.  State 19 is a
DIFFERENT shape from all of them: two head arms that are really one state
machine's two halves, a 200-entry scan whose result IS consumed (unlike
its own twin at `00722C`), a NEW small leaf (`005CEE`) that overloads two
fields believed already fully understood, a SECOND new leaf (`010D7C`)
neither `game.messages` nor anything else already recovered reads or
writes, and at least five more terminal addresses not yet even reached by
a hand trace.  Recovering it correctly needs: (1) `game.movement`'s own
`box_overlap_scan` extended or forked for a caller that consumes its
result (the 192-entry `0x14B42` kind table is itself unread ROM data, not
yet named); (2) a new `game.achievements`-adjacent leaf for `005CEE`
correcting the `ACHIEVEMENT_SLOTS`/`HIGHLIGHT_ID` module note above (both
fields are shared beyond the achievement tracker, not owned by it); (3) a
wholly new module for `010D7C`'s own icon/message spawn record; and (4)
tracing the five untouched terminal shapes past `005C14`.  This is
comparable in scope to states 0/1/14 (this project's own largest single
sessions), not a same-session extension of states 8/13/12/16/11's own
recipe.

## What was tried

- Linear disassembly of the raw ROM range around `005886` (as for the
  0058-005E dispatcher range generally) produced garbled instructions
  early this session, for the same reason state 19 was originally set
  aside: data is embedded in code across this range.  Trace-based
  analysis (`pathfacts.trace`/`.report` on real census fixtures) is the
  only reliable method here, as it was for every state recovered this
  session.
- Bucketed all 190 retained fixtures by `last_pc` (`pathfacts.trace(...,
  stop_pc=0x0075D6)`) to find the real terminal shapes before committing
  to any one arm's semantics -- the same technique that made states
  8/13/12/16/11 tractable in one sitting each. It surfaced ten shapes
  here, an order of magnitude more than any state closed this session,
  which is the concrete signal this is not a same-recipe leaf.
- Cross-checked `FFFFF22E`/`FFFFF236` against `game/achievements.py`'s own
  `ACHIEVEMENT_SLOTS`/`HIGHLIGHT_ID` constants and confirmed by address
  that `005CEE` reuses them with a DIFFERENT addressing convention (index
  register vs. four fixed offsets) -- a real, useful finding recorded
  here rather than acted on, since correcting `achievements.py`'s own
  module docstring and adding `005CEE`'s own composition is itself a unit
  of work past this session's remaining scope.
- Attempted a raw ROM byte diff between the state 19 inline box-scan copy
  (`0058D8`-`005924`) and `00722C` to see if the boundary plan could reuse
  a shared cost table the way state 11 reused state 12's own verbatim;
  the copies are NOT byte-identical (different opening instruction
  sequence for the same margin arithmetic), so state 19's own copy needs
  its own cost constants even though the ALGORITHM (confirmed via trace)
  is `game.movement.box_overlap_scan`'s own.

## Resolution (grinder, 18 September, states 19 and 18 recovered in full)

Once the coordinator's own remaining list closed, both states were
recovered together in one dedicated session rather than deferred further.
The box-overlap-scan copy (`00722C`'s own algorithm, a second,
separately-compiled instance, consumed here unlike its own twin's two
discard-only call sites at states 0/1), the new leaf `005CEE`
(`game.achievements.achievement_highlight_cycle`, correcting the module
note this blocker itself flagged: `ACHIEVEMENT_SLOTS`/`HIGHLIGHT_ID` are
shared beyond the achievement tracker, not owned by it), and the wholly
new leaf `010D7C` (`game.spawns.floating_icon_spawn`, a fourth subsystem:
a floating icon/message spawn record distinct from `game.messages`'s own
fields) are all now recovered, tested and verified.  All ten real
terminal shapes this blocker's own census found are witnessed and MATCH;
the arms this session did not trace past their own first branch (EA23
bit 1 alone at the pending/idle tails' own two-bit dispatch, and the box
scan's own kind-other/kind-out-of-range arms) remain declined by name,
confirmed unwitnessed by a full re-scan of every retained fixture (bit 1
is never independently set in any of the 190 + 118 retained fixtures; the
box scan's own found entry is always kind == 2).  States 18 and 19 turned
out to be the "one region, two gates" shape this blocker's own analysis
anticipated but did not confirm: NOT byte-identical heads (a raw ROM diff
of state 18's own first 400 bytes against state 19's differs in 369), but
branching into the SAME physical downstream code (`0058D2` the scan
entry, `005C14` the post-scan dispatch, `005CEE` the highlight cycle) --
confirmed directly via trace, not assumed by symmetry.

Two real, non-obvious facts the tracer found, not guessed. First, `001648`
(the icon upload) is called here with a POSITIVE D2 (the found entry's
own kind, e.g. `0x12`) at `005C36`'s own inline call --
`achievement_slot_reset`'s own docstring had read D2 as always `-1` from
its own single caller, but this is a second, independent witness of
`001648`'s own real-descriptor-upload arm, never before exercised by any
recorded fixture in this project.  Second, states 19/18's own two-jsr
"idle-cycle" arm (`005C98`-`005CEA`) is Aladdin's own "platform tail: a
run of them" shape applied for the first time in Gods: two real `001648`
calls back to back with RAM work in between, ceded as ONE span (the
prefix ends at the first `jsr`, `resume_pc` set past BOTH calls) rather
than chaining two seams -- confirmed necessary the hard way, via a real
"Seam return/frame mismatch" native error an early draft raised by
guarding the first call's own transient return-address slot, which the
second call legitimately reuses.

One shared-infrastructure limit surfaced and was NOT worked around by
touching shared code: `native/machine.cpp` caps the gate set at 64
(PortForge, pinned), and `camera-sprites` was already at 63 gates before
