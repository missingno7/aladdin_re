# Blocker: the movement states' shared hit-resolution subsystem (`008222`, `012DA0`, `012E5A`)

## Where

Reached from inside the player state machine's own movement-cluster
handlers, once `0075D6` (the shared tail, recovered this session,
`Gods: recover 0075D6 player state machine shared tail`) was gated and
its own state handlers became the next candidates per
`docs/gods/blockers/2026-09-17-005700.md`'s Decision.  Every state handler
disassembled this session in the frequency order the Decision names --
state 1 (`007282`), state 0 (`006FFE`), and, while surveying for a
tractable alternative, state 24 (`006AD8`, chosen because state 5's own
entry `00746A` turned out to be a **shared fallthrough of state 1's own
body**, not an independent handler with a clean boundary) -- all reach
this same web of not-yet-recovered routines on a real, non-rare fraction
of their own activations.  Full disassembly this session:
`00722C` (a 200-entry bounded box-overlap scan, result unused at its two
call sites in states 0/1), `008222` and its own helper `00837E`, `012DA0`
and `012E5A` (siblings) and their own shared helpers `012E32`/`012EE6`.

## Code

`NEW_GODS_SUBSYSTEM`.

## Observed

- **States are not small leaves.**  State 1's own body (`007282`-`007469`,
  before falling into state 5's own entry `00746A`) is itself
  ~150 instructions with a dozen branches; state 0's own body
  (`006FFE`-`00727B`ish) is nearly identical in shape (both read a
  caller-supplied record at `A0` -- set by `bsr 0063FA`, the already-
  recovered grid cell lookup -- test bytes at `$180`/`$181`/`$1`/`(a0)`
  of it, and branch through the same `FFFFEA1E`/`FFFFEA20`/`FFFFEA23`
  pad-intent words `game.player`'s own docstring already flags as
  unread this session).  State 5's own "entry" `00746A` is reached BOTH
  by a `bra.w` fallthrough from inside state 1's own body and by the
  dispatch table's own state-5 slot: it is shared code, not an
  independent handler, so the Decision's own "each state as a leaf
  owning its body" assumption does not hold uniformly across states.
- **`008222`** (`FFFFF1A2` reentrancy guard; a 40-entry list at `FFFFEF8E`,
  0x18-byte stride, scanned through the helper `00837E` across three
  chained sub-passes offset by `d5` 1/4/7; a found entry's own list
  pointer and index are stored into one of three slots,
  `FFFFF374`/`FFFFF378`/`FFFFF37C` with their own index words
  `FFFFF36E`/`FFFFF370`/`FFFFF372`) is a hit-list search structurally
  parallel to the already-recovered `game.hazard.proximity_search`
  (`00F828`, a 40-entry pool scan too) but over a different table with a
  different record shape and a different (unread) selection rule.  A
  full-history tally at state 1's own entry (`007282`, `fb408bc75597`,
  34,904 frames, 3,181 activations): `008222` reached on **800** of them
  (25%); `00722C` (state 0/1's OWN unrelated 200-entry box scan, whose
  returned CCR is provably unused at either call site) on only 21.
- **`012DA0`/`012E5A`** are two near-identical siblings, each consuming
  whichever of `FFFFF374`/`F378`/`F37C` `008222` last populated: a
  non-null slot's own type word (through its list record) selects a ROM
  jump table at `012D04` (doubled index), which selects a SECOND jump
  table at `012C3E` from a field of the type's own descriptor (offset
  `$14` for `012DA0`'s own first two slots, `$10` for `012E5A`'s), and
  `jmp`s into a per-object-type handler -- an undiscovered dispatch
  family, not a leaf.  Witnessed on state 24 (`006AD8`, gated by its own
  `d7==1`, a counter value every sufficiently long activation of that
  state reaches): **7 of 14 retained path classes** (half) call `012DA0`,
  and it reaches all the way into `012E32`'s own per-type `jmp` on at
  least one retained fixture (`006AD8-entry-p0.state`, calls
  `012DCE -> 012E32 -> rts 013210`).  `012DA0`/`012E5A` both write the
  word `FFFFFDF6` (`31fc0035fdf6`, `move.w #$35,$fdf6.w`) unconditionally
  before doing anything else -- almost certainly the same sound-request
  queue `game.hazard.SOUND_COMMAND` (`0xFFFFFDF4`) already names two
  bytes away, a fact worth confirming before naming it.

## Why the current mechanism does not fit

Recipe 6a needs a handler that is either a small leaf or a call into
already-recovered code.  Every movement-cluster state handler examined
this session (0, 1, 5's own shared entry, 24) reaches `008222` or
`012DA0`/`012E5A` on a real, frequently-witnessed fraction of its own
activations -- not a rare, safely-declinable edge the way `00755A` or the
follow point's own clamps were for the shared tail.  Declining every
occurrence that reaches this web would leave most states' own admission
rate too low to be a meaningful recovery, and the states cannot be
recovered "around" it: `008222` sets persistent state (`FFFFF374` et al.)
that `012DA0`/`012E5A` read back, often several ticks later, so the two
halves are not independent leaves either.  This is squarely
`NEW_GODS_SUBSYSTEM`: a hit-list search, its own per-object-type dispatch
tables, and whatever `012E32`'s/`012EE6`'s own per-type handlers do (not
yet disassembled) all need their own naming and evidence before any
movement-cluster state -- or `008222`/`012DA0`/`012E5A` themselves as
leaves -- can be planned.

## What was tried

- Disassembled states 1 (`007282`-`0074F0`) and 0 (`006FFE`-`007282`) in
  full: found them near-identical in shape and both dependent on
  `00722C` and `008222`.
- Disassembled `00722C` in full: a bounded (`dbra`, max 200) box-overlap
  scan over a fixed 8-byte-stride table at `FFFF4342`, returning its
  result through the CCR via a `rtr` trick -- confirmed structurally
  recoverable (RAM-only, bounded) but **not useful yet**: both witnessed
  call sites (states 0 and 1) discard its result outright (no
  conditional branch reads the CCR before the next flag-setting
  instruction), so recovering it does not by itself unblock either
  state.
- Disassembled `008222` and its helper `00837E` in full; found the
  three-slot hit-record structure and the reentrancy guard
  (`FFFFF1A2`/`FFFFF23C`).
- Surveyed state 24 (`006AD8`) as a candidate simpler than 0/1/5: found
  it much shorter (~12 instructions) but its own `012DA0` call, gated on
  a counter value (`d7==1`) every multi-tick activation reaches, is
  witnessed on half its own retained path classes -- not the rare edge
  hoped for.
- Disassembled `012DA0`/`012E5A` and their shared tail-call targets
  `012E32`/`012EE6` far enough to find the two-level per-object-type
  dispatch (`012D04`, `012C3E`) and the unconditional `FFFFFDF6` sound
  write; did not disassemble the per-type handlers themselves (real,
  deep, unrelated to this session's remaining budget).

## Addendum, 18 September: `008222` fully disassembled; still not a leaf on its own

Full disassembly this session, `008222`-`00837E` (008222-008390) and its
own three sub-passes read to their own tail: the reentrancy guard
(`FFFFF1A2`) shares its early-return code with `00837E`'s own "occupied"
return (`00838E moveq #$1,d0; rts`, one instruction pair, two callers);
the real search runs up to THREE independent sub-passes over three lists
(`FFFFEF8E`, `FFFFF020`, `FFFFF0B2`), each gated by its own list's
leading count word (`-2(a3)`, negative skips the whole sub-pass) and each
retrying up to three consecutive list entries (`00837E`'s own "all three
status words -- offsets 0/8/0x10 -- are zero" test, `lea $18(a3),a3`
between retries) before giving up.  What is NOT yet named: the first
sub-pass's own count indexes a flat 0x50-byte-stride table at
`FFFFF552` directly; the second and third instead double the SAME count
as an index into the per-object-type POINTER table at `012D04` --
**the same table `012DA0`/`012E5A`'s own two-level dispatch already
reads** -- and read offset `+0xA` of whatever it points to.  Both reads
land in `D4`/`D6`, and `D6`'s own value (not `D0`) gates a further
one-shot latch (`FFFFF23C`) on a found entry, whose own meaning (what
sets it, what reads it back) is not traced this session.  Structurally
this is `proximity_search`'s own shape three times over, but the
`F552`/`012D04+0xA` lookups and the `F23C` latch are new data this
session does not have a name for, and naming them from `012D04`'s own
target structures is exactly the work `012DA0`/`012E5A`'s per-type
handlers still need (deferred, per the original finding above) -- so
`008222` cannot yet be planned as a self-contained leaf independent of
that naming, contrary to what this Next Question hoped.

A fresh census (`artifacts/gods/evidence/census-008222`, `--classifier
kind`, `fb408bc75597`, default `--max-classes 32`) confirms the shape at
scale: 800 occurrences, 62 signature classes.  92 of 739 `kind00`
occurrences are the reentrancy-guard early return (4 instructions, no
writes); the rest run 23-113 instructions calling `00837E` one to six
times (one to three attempts per sub-pass, times up to three sub-passes)
-- every retained fixture stays within work RAM, no device access, no
call deeper than `00837E` itself.  One concrete fixture traced in full
(`008222-kind00-p9.state`): the guard was clear, sub-pass 1 found a
match on its own first entry (stored `FFFFEF8E`/`FFFFF36E` into
`FFFFF374`), sub-pass 2 was skipped entirely (`FFFFF020`'s own count
negative), sub-pass 3 also found a match on its own first entry (stored
`FFFFF0B2`/`0x13` into `FFFFF37C`/`FFFFF372`) -- `F23C` was NOT set on
either found entry, both having `D6 != 1` at the point of the check.

Bounded and RAM-only in every retained fixture; the remaining blocker is
naming `FFFFF552`'s own 0x50-byte records and `012D04`'s own pointer
targets' `+0xA` field (and what reads `FFFFF23C` back), not the search's
own control flow.  Next question unchanged in kind, sharpened in target:
whichever of `012DA0`/`012E5A`'s own per-type handlers is disassembled
first should also settle what `012D04`'s targets' own `+0xA` field and
`FFFFF23C` mean, since `008222` already reads both without being able to
name them.
