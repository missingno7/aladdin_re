## Why the current mechanism does not fit

Recipe 6a needs a handler that is either a small leaf or a call into
already-recovered code.  Every movement-cluster state handler examined
this session (0, 1, 5's own shared entry, 24) reaches `008222` or
`012DA0`/`012E5A` on a real, frequently-witnessed fraction of its own
activations -- not a rare, safely-declinable edge the way `00755A` or the
follow point's own clamps were for the shared tail.  Declining every
occurrence that reaches this web would leave most states' own admission
rate too low to be a meaningful recovery, and the states cannot be
recovered "around" it: `008222` sets persistent state (`FFFFF374` et al.)
that `012DA0`/`012E5A` read back, often several ticks later, so the two
halves are not independent leaves either.  This is squarely
`NEW_GODS_SUBSYSTEM`: a hit-list search, its own per-object-type dispatch
tables, and whatever `012E32`'s/`012EE6`'s own per-type handlers do (not
yet disassembled) all need their own naming and evidence before any
movement-cluster state -- or `008222`/`012DA0`/`012E5A` themselves as
leaves -- can be planned.

## Addendum, 18 September: `008222` fully disassembled; still not a leaf on its own

Full disassembly this session, `008222`-`00837E` (008222-008390) and its
own three sub-passes read to their own tail: the reentrancy guard
(`FFFFF1A2`) shares its early-return code with `00837E`'s own "occupied"
return (`00838E moveq #$1,d0; rts`, one instruction pair, two callers);
the real search runs up to THREE independent sub-passes over three lists
(`FFFFEF8E`, `FFFFF020`, `FFFFF0B2`), each gated by its own list's
leading count word (`-2(a3)`, negative skips the whole sub-pass) and each
retrying up to three consecutive list entries (`00837E`'s own "all three
status words -- offsets 0/8/0x10 -- are zero" test, `lea $18(a3),a3`
between retries) before giving up.  What is NOT yet named: the first
sub-pass's own count indexes a flat 0x50-byte-stride table at
`FFFFF552` directly; the second and third instead double the SAME count
as an index into the per-object-type POINTER table at `012D04` --
**the same table `012DA0`/`012E5A`'s own two-level dispatch already
reads** -- and read offset `+0xA` of whatever it points to.  Both reads
land in `D4`/`D6`, and `D6`'s own value (not `D0`) gates a further
one-shot latch (`FFFFF23C`) on a found entry, whose own meaning (what
sets it, what reads it back) is not traced this session.  Structurally
this is `proximity_search`'s own shape three times over, but the
`F552`/`012D04+0xA` lookups and the `F23C` latch are new data this
session does not have a name for, and naming them from `012D04`'s own
target structures is exactly the work `012DA0`/`012E5A`'s per-type
handlers still need (deferred, per the original finding above) -- so
`008222` cannot yet be planned as a self-contained leaf independent of
that naming, contrary to what this Next Question hoped.

A fresh census (`artifacts/gods/evidence/census-008222`, `--classifier

## Decision (supervisor, 18 September)

The data is already named.  `012D04` is `pickups.ITEM_RECORDS`: eleven
longs, each the address of an item's work-RAM record — and those records
are the eleven 0x50-byte records at `FFF552`, `FFF5A2`, … `FFF872` (the
pointer table's own contents), which `game/pickups.py`'s docstring
already states.  The first sub-pass indexing `FFF552` by count and the
other two indexing `012D04` by the doubled count read the **same
records** two ways.  `+0xA` is the word after `ITEM_VALUE` (`+8`) in that
record; name it by what `008222` does with it (the value it latches into
`FFF23C` on a found entry — `ITEM_CONTACT_WORD`, or better if the ROM
says more), and `FFF23C` is the search's own contact latch
(`CONTACT_LATCH`, cleared at `008230`, set once on a hit; what reads it
back is a fact for the ledger, not a precondition of the plan).  The
three lists are the three collectible lists the tick's phase 14
(`013342`) walks: `FFEF8C`/`FFF01E`/`FFF0B0` count words, entries at `+2`.

A bounded, RAM-only region whose reads come from tables the ROM names
and whose writes are two words is a leaf; naming a field by its role is
enough to plan it (that is how `ITEM_CONSUMES_SLOT` was named).  Recover
`008222` with `00837E` as `contact_search` in `game/pickups.py` (three
sub-passes, each retrying up to three consecutive entries), all witnessed
path classes, the usual ladder; then `012DA0`/`012E5A` as the family over
the item type the record names; then the movement states over it.
